# Better Auth + Google OAuth contract

Research date: 2026-07-17

## Question

What does Productivity Up need to support Google sign-in correctly across localhost, preview, and production, and what are the relevant Better Auth contracts for callbacks, verified email, account linking, failures, and automated tests?

## Short answer

**A live domain is not required to implement or test Google sign-in locally.** Google explicitly permits HTTP redirect URIs for `localhost` and localhost IP addresses, and Better Auth documents `http://localhost:3000/api/auth/callback/google` as its local-development example. The actual port must match the app, and the URI must otherwise match exactly. [Google OAuth client validation rules](https://support.google.com/cloud/answer/15549257?hl=en), [Better Auth Google provider](https://better-auth.com/docs/authentication/google)

A public production launch is different: Google requires HTTPS for non-local redirect URIs, and every production OAuth app must have a publicly accessible homepage on a verified domain that the developer owns, with functionality, privacy-policy, and terms links. [Google OAuth 2.0 policies](https://developers.google.com/identity/protocols/oauth2/policies), [Google app-branding requirements](https://support.google.com/cloud/answer/15549049?hl=en)

Ephemeral preview deployments are the awkward case. Google does not allow wildcards in redirect URIs, while every authorization request must use an exact registered URI. A fixed preview hostname can be registered directly; arbitrary per-commit hostnames need either individually registered exact callbacks or a stable callback proxy. Better Auth provides an OAuth Proxy plugin specifically for unknown preview/development URLs. [Google OAuth client validation rules](https://support.google.com/cloud/answer/15549257?hl=en), [Google web-server OAuth flow](https://developers.google.com/identity/protocols/oauth2/web-server), [Better Auth OAuth Proxy](https://better-auth.com/docs/plugins/oauth-proxy)

## Environment contract

| Environment | Google-side callback | Better Auth-side URL/origin | Domain requirement |
| --- | --- | --- | --- |
| Local development | Register the exact local callback, for example `http://localhost:3000/api/auth/callback/google`; localhost may use HTTP, and a non-default port is part of the exact URI. [Google OAuth client validation rules](https://support.google.com/cloud/answer/15549257?hl=en), [Better Auth Google provider](https://better-auth.com/docs/authentication/google) | Set the local `BETTER_AUTH_URL`/`baseURL` explicitly; Better Auth uses it to construct the callback. [Better Auth installation](https://better-auth.com/docs/installation), [Better Auth Google provider](https://better-auth.com/docs/authentication/google) | No live domain is required. [Google OAuth client validation rules](https://support.google.com/cloud/answer/15549257?hl=en) |
| Stable preview/staging | Register an exact HTTPS callback on the stable preview hostname, such as `https://preview.example.com/api/auth/callback/google`; scheme, host, path, case, and trailing slash must match. [Google web-server OAuth flow](https://developers.google.com/identity/protocols/oauth2/web-server) | Give that deployment its own explicit base URL and include its origin in Better Auth's trusted origins. Better Auth trusts its base URL by default and validates redirect destinations against trusted origins. [Better Auth options](https://better-auth.com/docs/reference/options), [Better Auth security](https://better-auth.com/docs/reference/security) | A reachable HTTPS hostname is required for a non-local callback. [Google OAuth client validation rules](https://support.google.com/cloud/answer/15549257?hl=en) |
| Ephemeral previews | Google cannot register `https://*.preview.example.com/...` because redirect-URI wildcards are forbidden. Use exact registration per preview or send all provider callbacks through one stable proxy callback. [Google OAuth client validation rules](https://support.google.com/cloud/answer/15549257?hl=en), [Better Auth OAuth Proxy](https://better-auth.com/docs/plugins/oauth-proxy) | The OAuth Proxy requires preview/local origins in `trustedOrigins` and a dedicated proxy secret shared by all participating environments; it then returns encrypted profile data to the initiating preview, which creates its own user/session. [Better Auth OAuth Proxy](https://better-auth.com/docs/plugins/oauth-proxy) | The preview itself need not have a pre-registered callback if a stable proxy is used, but the proxy does need a stable HTTPS hostname. [Better Auth OAuth Proxy](https://better-auth.com/docs/plugins/oauth-proxy) |
| Production | Register the exact production HTTPS callback, normally `https://app.example.com/api/auth/callback/google`. [Better Auth Google provider](https://better-auth.com/docs/authentication/google), [Google OAuth client validation rules](https://support.google.com/cloud/answer/15549257?hl=en) | Set the production base URL explicitly and keep production redirect/callback targets within trusted origins. [Better Auth options](https://better-auth.com/docs/reference/options), [Better Auth security](https://better-auth.com/docs/reference/security) | A public homepage on a verified owned domain is required for a production OAuth app. [Google OAuth 2.0 policies](https://developers.google.com/identity/protocols/oauth2/policies) |

Google's policy requires separate Google Cloud projects for deployment tiers such as development, staging, and production. Therefore, the policy-aligned interpretation of Better Auth's proxy pattern is to use a stable non-production proxy/client for preview work and a separate production project/client for production, rather than sharing the production Google client with previews. [Google OAuth 2.0 policies](https://developers.google.com/identity/protocols/oauth2/policies), [Better Auth OAuth Proxy](https://better-auth.com/docs/plugins/oauth-proxy)

## Authorized origins, redirect URIs, and trusted origins are different controls

- A Google **authorized redirect URI** is the server endpoint to which Google returns the authorization response. Better Auth's default provider callback is `/api/auth/callback/google`; a custom Better Auth `basePath` or provider `redirectURI` changes what must be registered. [Google OAuth client validation rules](https://support.google.com/cloud/answer/15549257?hl=en), [Better Auth OAuth concepts](https://better-auth.com/docs/concepts/oauth)
- A Google **authorized JavaScript origin** is needed when browser JavaScript directly calls Google APIs. An origin contains only scheme, host, and optional non-default port—no path, query, or fragment—and localhost is exempt from HTTPS. The ordinary Better Auth authorization-code flow is server-callback based, so its required Google-side setting is the redirect URI; add JavaScript origins only if a client-side Google Identity Services/API integration is also introduced. [Google OAuth client validation rules](https://support.google.com/cloud/answer/15549257?hl=en), [Better Auth Google provider](https://better-auth.com/docs/authentication/google)
- A Better Auth **trusted origin** is Better Auth's own allowlist for request-origin checks and redirect destinations such as `callbackURL`, `errorCallbackURL`, and `newUserCallbackURL`. It is not a substitute for either Google setting. Disabling Better Auth's origin check also disables CSRF protection for backward compatibility and enables open-redirect risk, so it should not be used to make preview URLs work. [Better Auth security](https://better-auth.com/docs/reference/security)

## Credentials and configuration

The minimum provider configuration is a Google web client ID and client secret under `socialProviders.google`, plus an explicit Better Auth base URL. Better Auth uses that base URL to build the callback sent to Google; leaving production to infer localhost is a documented cause of `redirect_uri_mismatch`. [Better Auth Google provider](https://better-auth.com/docs/authentication/google), [Better Auth options](https://better-auth.com/docs/reference/options)

The Google client secret belongs only on the server. Google classifies web-server apps as private clients able to hold a secret, instructs developers to store it securely, and forbids committing OAuth client credentials to public repositories. Better Auth separately requires a high-entropy secret of at least 32 characters for its encryption and hashing. [Google OAuth client management](https://support.google.com/cloud/answer/15549257?hl=en), [Google OAuth 2.0 policies](https://developers.google.com/identity/protocols/oauth2/policies), [Better Auth installation](https://better-auth.com/docs/installation)

Use tier-specific values for at least the Google client ID/secret and Better Auth base URL. Better Auth's global secret should also remain environment-specific; the exception is the OAuth Proxy's dedicated `secret`, which must be identical on the proxy and participating preview/local deployments. Better Auth recommends a dedicated proxy secret instead of sharing `BETTER_AUTH_SECRET`, limiting compromise to the proxy flow's short payload lifetime. [Google OAuth 2.0 policies](https://developers.google.com/identity/protocols/oauth2/policies), [Better Auth OAuth Proxy](https://better-auth.com/docs/plugins/oauth-proxy)

Better Auth account records can store provider access, refresh, and ID tokens, while `account.encryptOAuthTokens` defaults to `false`. Google requires OAuth tokens to be encrypted at rest. If Google tokens are retained, the implementation specification should therefore enable Better Auth token encryption or avoid persisting tokens that the product does not need. [Better Auth users and accounts](https://better-auth.com/docs/concepts/users-accounts), [Better Auth options](https://better-auth.com/docs/reference/options), [Google OAuth 2.0 policies](https://developers.google.com/identity/protocols/oauth2/policies)

For sign-in only, request only identity scopes. Google's current audience rules explicitly exempt Sign in with Google and the `openid`, `userinfo.email`, and `userinfo.profile` subset from Testing-mode test-user warnings and seven-day authorization expiry. Adding other Google API scopes removes that exception and may require sensitive/restricted-scope verification. [Google app audience](https://support.google.com/cloud/answer/15549945?hl=en), [Google OAuth verification](https://support.google.com/cloud/answer/13463073?hl=en)

## Callback and redirect behavior

1. The client starts the flow with `authClient.signIn.social({ provider: "google", ... })`. It may supply `callbackURL` for normal success, `newUserCallbackURL` for a newly registered user, and `errorCallbackURL` for failure; `disableRedirect` suppresses automatic provider navigation when the caller needs the generated response. [Better Auth basic usage](https://better-auth.com/docs/basic-usage)
2. Better Auth sends the browser to Google using the authorization-code flow and includes its callback plus OAuth `state`. Google requires the callback to exactly match the registered URI and returns either a `code` or an error such as `access_denied` on the callback query string. [Google web-server OAuth flow](https://developers.google.com/identity/protocols/oauth2/web-server)
3. Better Auth verifies state, exchanges the code, obtains the Google profile, creates or links the provider account, creates a session, and redirects to the stored application callback. Better Auth uses state to retain the safe callback destination; starting at the callback manually omits that state and produces callback/state errors. [Better Auth OAuth concepts](https://better-auth.com/docs/concepts/oauth), [Better Auth `no_callback_url`](https://better-auth.com/docs/reference/errors/no_callback_url), [Better Auth `state_mismatch`](https://better-auth.com/docs/reference/errors/state_mismatch)
4. Better Auth validates application redirect URLs against trusted origins. Failures that cannot continue are routed through the configured error callback or Better Auth's `/api/auth/error` behavior; documented OAuth errors include invalid/missing code or state, missing email, account-linking conflicts, user/session creation failures, and disabled signup. [Better Auth security](https://better-auth.com/docs/reference/security), [Better Auth errors](https://better-auth.com/docs/reference/errors)

The product specification should give Google sign-in a deliberate success destination, a deliberate first-user destination if onboarding differs, and an application-owned error page that translates stable error codes into retryable/corrective UX. This follows from Better Auth's separate callback fields and documented OAuth error taxonomy. [Better Auth basic usage](https://better-auth.com/docs/basic-usage), [Better Auth errors](https://better-auth.com/docs/reference/errors)

## Verified email and account linking

Google's ID token includes `email` and `email_verified` when the `email` scope is requested, but Google says `sub`—not email—is the stable Google-account identifier because an email can change. Better Auth's provider account should consequently remain identified by Google's provider account ID, while email is used only for the explicit cross-provider linking policy. [Google OpenID Connect reference](https://developers.google.com/identity/openid-connect/reference)

Better Auth enables account linking by default. On OAuth sign-in, if the returned email matches an existing local user and the provider marks it verified (or is configured as trusted), Better Auth implicitly links the Google provider account to that user rather than creating a second identity. With `disableImplicitLinking: true`, the same attempt fails with `account_not_linked`; a signed-in user can still explicitly attach Google through `linkSocial()`. [Better Auth users and accounts](https://better-auth.com/docs/concepts/users-accounts), [Better Auth options](https://better-auth.com/docs/reference/options)

There is an important semantic mismatch to decide explicitly:

- Better Auth treats a provider's `email_verified` signal as sufficient for default same-email linking. [Better Auth users and accounts](https://better-auth.com/docs/concepts/users-accounts)
- Google says it is authoritative for ownership when the address is Gmail, or when `email_verified` is true and the token has an `hd` Google Workspace claim. For a non-Gmail Google Account without `hd`, `email_verified` can still be true even though ownership of that third-party mailbox may have changed since Google first verified it. [Google ID-token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)

Thus the default Better Auth convenience policy has a residual takeover risk for an existing password account whose address is a non-Gmail, non-Workspace email reused by a Google Account. A safety-first B2C policy would set `disableImplicitLinking: true` and require the user to authenticate the existing Productivity Up account before explicitly linking Google; retaining implicit linking is a conscious convenience-over-assurance choice. This recommendation is an inference from Better Auth's linking rule and Google's narrower statement of when it is authoritative. [Better Auth users and accounts](https://better-auth.com/docs/concepts/users-accounts), [Google ID-token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)

Explicit linking defaults are conservative in other ways: different-email linking requires `allowDifferentEmails: true`; linking does not replace the local user's email or `emailVerified`; and unlinking the only remaining account is blocked unless `allowUnlinkingAll` is enabled. [Better Auth users and accounts](https://better-auth.com/docs/concepts/users-accounts), [Better Auth options](https://better-auth.com/docs/reference/options)

## Preview-specific failure modes

Direct preview callbacks fail as `redirect_uri_mismatch` when the URI is not registered exactly. Proxy flows additionally fail with `state_mismatch` if preview and proxy do not share the OAuth Proxy's dedicated secret, and the preview/local origins must be present in Better Auth's trusted origins. [Google web-server OAuth flow](https://developers.google.com/identity/protocols/oauth2/web-server), [Better Auth OAuth Proxy](https://better-auth.com/docs/plugins/oauth-proxy)

OAuth state is time- and browser-context-sensitive. Better Auth documents failures from expired state, missing/corrupted cookies, replaying a callback, concurrent sign-in tabs, secret rotation during the flow, non-shared verification storage across server instances, and preview/production domain mismatches. The error UX should tell the user to restart sign-in rather than retrying or refreshing the callback URL. [Better Auth `state_mismatch`](https://better-auth.com/docs/reference/errors/state_mismatch)

## Automated testing and agent access

Routine CI should not automate Google's username/password pages. Google says it may block sign-ins from browsers controlled by software automation, and its OAuth policy requires a secure user-visible browser rather than an embedded user agent controlled by the developer. A live Google round trip is therefore unsuitable as the gate for every deterministic test run. [Google supported-browser guidance](https://support.google.com/accounts/answer/7675428?hl=en-uk), [Google OAuth 2.0 policies](https://developers.google.com/identity/protocols/oauth2/policies)

Better Auth's official Test Utils plugin is the supported bypass for application integration and E2E tests. In a separate test-only auth instance it can create/persist users, create authenticated sessions, return request headers, and return Playwright/Puppeteer-compatible cookies. The plugin exposes privileged server-side helpers and should be kept out of production auth configuration. [Better Auth Test Utils](https://better-auth.com/docs/plugins/test-utils)

Recommended test split:

- **Most E2E and agent journeys:** create an isolated test user, call Test Utils `login()`/`getCookies()`, inject the returned cookie into the browser context, and start on the protected page. This tests Productivity Up's authenticated behavior without sharing Google credentials or depending on Google's UI. [Better Auth Test Utils](https://better-auth.com/docs/plugins/test-utils)
- **Auth-boundary integration tests:** test signed-out route guards, the Google button's initiation of Better Auth social sign-in, allowed callback/error destinations, session creation behavior, and account-linking policy using isolated databases and Better Auth APIs/helpers; do not disable CSRF or origin validation for tests. Better Auth documents both the test helpers and the security consequences of disabled checks. [Better Auth Test Utils](https://better-auth.com/docs/plugins/test-utils), [Better Auth security](https://better-auth.com/docs/reference/security)
- **Small real-provider smoke suite:** manually or on a low-frequency monitored run, use a dedicated non-production Google Cloud project and dedicated Google account in a normal supported browser to cover consent, callback, new-user creation, repeat sign-in, cancellation, and whichever same-email linking policy is selected. Google requires separate projects for test/staging and production, and automation-controlled browsers may be rejected. [Google OAuth 2.0 policies](https://developers.google.com/identity/protocols/oauth2/policies), [Google supported-browser guidance](https://support.google.com/accounts/answer/7675428?hl=en-uk)
- **If scopes grow beyond identity:** expect Testing-mode authorization and refresh tokens to expire after seven days, and plan re-consent plus verification-specific testing. The seven-day expiry does not apply to Sign in with Google/basic identity-only scopes. [Google app audience](https://support.google.com/cloud/answer/15549945?hl=en)

An agent-access mechanism should exist only in test/development infrastructure, backed by an isolated database and unavailable in production. Better Auth's test-only session/cookie helpers meet that requirement without adding a public bypass route. [Better Auth Test Utils](https://better-auth.com/docs/plugins/test-utils)

## Decision-ready conclusions

1. Implement local Google sign-in now; no deployed domain is needed. Register the exact localhost callback and set the local Better Auth base URL. [Better Auth Google provider](https://better-auth.com/docs/authentication/google)
2. Use separate Google Cloud projects/credentials for non-production and production. Keep production credentials and Better Auth secrets out of preview/local environments. [Google OAuth 2.0 policies](https://developers.google.com/identity/protocols/oauth2/policies)
3. Prefer a stable non-production callback/proxy for ephemeral previews; Google wildcard callbacks are not supported. Use a dedicated shared OAuth Proxy secret and explicit preview trusted origins. [Google OAuth client validation rules](https://support.google.com/cloud/answer/15549257?hl=en), [Better Auth OAuth Proxy](https://better-auth.com/docs/plugins/oauth-proxy)
4. Keep Google scopes to identity only until the product genuinely needs Google API access; this avoids the additional Testing-mode expiry and sensitive/restricted-scope verification path. [Google app audience](https://support.google.com/cloud/answer/15549945?hl=en), [Google OAuth verification](https://support.google.com/cloud/answer/13463073?hl=en)
5. Make account linking a named product/security decision. The conservative choice is explicit linking because Google's `email_verified` is not authoritative for every third-party email address, while Better Auth implicitly links every verified same-email provider by default. [Google ID-token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token), [Better Auth users and accounts](https://better-auth.com/docs/concepts/users-accounts)
6. Use Better Auth Test Utils for automated/agent session injection and reserve real Google UI for a small smoke suite in a normal browser. [Better Auth Test Utils](https://better-auth.com/docs/plugins/test-utils), [Google supported-browser guidance](https://support.google.com/accounts/answer/7675428?hl=en-uk)
