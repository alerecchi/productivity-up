# Public-launch B2C authentication baseline

Research date: 2026-07-17  
Question: What should a public B2C browser app treat as launch-critical, important follow-up, or optional in its authentication and account lifecycle?

## Bottom line

For Productivity Up, the public-launch baseline should be a **complete lifecycle**, not merely working sign-up and sign-in screens: email/password registration and sign-in; verified email ownership; Google sign-in with safe account linking; password reset; transactional-email delivery; protected, expiring sessions; current-session logout; abuse resistance; and reverified account deletion. Clerk and WorkOS both make verification, recovery, social login, linked identities, sessions, and anti-abuse part of their normal authentication surface, even though neither publishes a universal “B2C launch tiers” model. Clerk's prebuilt email/password flow verifies the email before finalizing a session, while WorkOS requires email verification by default before authentication succeeds ([Clerk email/password flow](https://clerk.com/docs/guides/development/custom-flows/authentication/email-password), [WorkOS identity linking](https://workos.com/docs/authkit/identity-linking)).

The tiers below are therefore a planning recommendation synthesized from provider behavior and security standards, not labels assigned by Clerk or WorkOS. “Launch-critical” means that omitting the capability would leave a promised entry path broken, make a common loss-of-access case unrecoverable, or leave an obvious account-takeover/session-lifecycle gap. “Important follow-up” means a low-risk personal todo app can launch without it if the limitation is deliberate and documented. “Optional” means an alternate credential or provider convenience rather than a prerequisite for a coherent first release.

## Capability tiers

### Launch-critical

| Capability | Product expectation | Provider and standards evidence |
| --- | --- | --- |
| Complete email/password registration and sign-in | Handle success, validation errors, already-used identifiers, unverified users, interrupted attempts, loading/double-submit prevention, and a deliberate post-authentication destination. A user must not reach protected data until the authentication attempt and required verification are complete. | Clerk models sign-up as a multi-step attempt that sends and verifies an email code before `finalize()` activates the session; it also exposes incomplete/pending states rather than treating credential submission as sufficient ([Clerk email/password flow](https://clerk.com/docs/guides/development/custom-flows/authentication/email-password), [Clerk session tasks](https://clerk.com/docs/guides/configure/session-tasks)). WorkOS returns an `email_verification_required` state and does not authenticate an unverified email user ([WorkOS authentication API](https://workos.com/docs/reference/authkit/authentication)). |
| Email ownership verification | Verify the primary email before granting normal account access. Support resend, expired/incorrect code, restarting the flow, and correcting a mistyped address. | WorkOS requires verification by default across password, OAuth, and SSO identities; Clerk enables verification at sign-up by default in its documented email/password setup ([WorkOS users and organizations](https://workos.com/docs/authkit/users-organizations), [Clerk email/password flow](https://clerk.com/docs/guides/development/custom-flows/authentication/email-password)). |
| Password recovery | Offer “forgot password” from sign-in, deliver a single-use code or token, let the user set a new password, handle expiry/retry, and return them to a clear authenticated or signed-out state. Decide whether reset revokes other sessions. | Clerk calls forgot-password common, documents the full request-code/verify/set-password flow, and exposes `signOutOfOtherSessions`; WorkOS Hosted UI includes password reset, while custom delivery exposes password-reset events and tokens ([Clerk forgot password](https://clerk.com/docs/guides/development/custom-flows/authentication/forgot-password), [WorkOS Hosted UI](https://workos.com/docs/authkit/hosted-ui), [WorkOS custom emails](https://workos.com/docs/authkit/custom-emails)). OWASP's testing guidance says password-authenticated applications need a way to regain access after a forgotten password ([OWASP password-reset testing](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication_Testing/09-Testing_for_Weak_Password_Change_or_Reset_Functionalities)). |
| Google sign-in as a real end-to-end path | Because Productivity Up already presents Google as a sign-in choice, launch requires provider configuration, initiation, callback, cancellation/error handling, account creation, safe return-to behavior, and a tested production configuration. A dead or partial button is not a launchable capability. | Both providers treat social login as a normal consumer method. Clerk says social sign-in and sign-up are equivalent and requires custom provider credentials in production; WorkOS lists OAuth among typical consumer methods and separates staging from production redirect/client configuration ([Clerk social connections](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/overview), [WorkOS modeling](https://workos.com/docs/authkit/modeling-your-app), [WorkOS environments](https://workos.com/docs/authkit/environments)). |
| Safe identity linking | A password account and Google identity with the same verified email must resolve to one user without silently trusting an unverified provider claim. Define behavior for an existing unverified password account, a provider without a verified email, and email mismatch. | Clerk links on matching email but adds verification/credential checks when either side is unverified; WorkOS links a new credential only after it can verify inbox access and refuses to complete unsafe linking ([Clerk OAuth account linking](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/account-linking), [WorkOS identity linking](https://workos.com/docs/authkit/identity-linking)). OAuth security best current practice also requires exact redirect protections and PKCE for authorization-code flows, including web clients ([RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700)). |
| Transactional auth email delivery | Verification and reset emails must be enabled in every deployed environment, carry recognizable product/sender information, link or code into the correct environment, and be tested end-to-end. Decide who owns templates, delivery, retries, and delivery observability. | Clerk can deliver customizable system templates or hand delivery to the application through `emails.created`; WorkOS can deliver verification/reset email by default or expose the lifecycle objects/events for custom delivery ([Clerk email templates](https://clerk.com/docs/guides/customizing-clerk/email-sms-templates), [WorkOS custom emails](https://workos.com/docs/authkit/custom-emails)). Both providers require production-specific configuration rather than assuming development settings carry over ([Clerk production deployment](https://clerk.com/docs/guides/development/deployment/production), [WorkOS environments](https://workos.com/docs/authkit/environments)). |
| Secure session lifecycle | Authenticate every protected server request, use secure browser cookie/token storage, refresh or expire sessions deliberately, prevent incomplete auth states from accessing data, and provide logout that actually invalidates the app session. Decide maximum lifetime and what occurs after password reset/deletion. | WorkOS says access tokens should be stored in secure cookies and validated by the backend on every request, and its logout flow removes the app cookie and ends the WorkOS session ([WorkOS sessions](https://workos.com/docs/authkit/sessions)). Clerk requires at least one session lifetime limit and provides explicit sign-out/revocation behavior ([Clerk session options](https://clerk.com/docs/guides/secure/session-options), [Clerk sign-out flow](https://clerk.com/docs/guides/development/custom-flows/authentication/sign-out)). OWASP treats user-initiated session termination as a core secure-web behavior ([OWASP logout testing](https://owasp.org/www-project-web-security-testing-guide/stable/4-Web_Application_Security_Testing/06-Session_Management_Testing/06-Testing_for_Logout_Functionality)). |
| Password and abuse protections | Use rate limits for failed authentication and recovery attempts, reject common/compromised passwords, permit password-manager autofill/paste, avoid arbitrary composition/rotation rules, and prevent automated sign-up/sign-in abuse. Responses to unauthenticated recovery/sign-in requests should not unnecessarily disclose whether an account exists. | NIST SP 800-63B requires failed-attempt rate limiting and a blocklist of common/compromised passwords, recommends password-manager/autofill support, and rejects arbitrary composition and periodic-rotation rules ([NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)). Clerk exposes bot, user-enumeration, and breached-password protections; WorkOS advertises automatic bot detection/blocking as part of AuthKit ([Clerk security overview](https://clerk.com/docs/guides/secure/overview), [WorkOS AuthKit overview](https://workos.com/docs/authkit/overview)). |
| Account deletion with recent reauthentication | Provide an authenticated, deliberate deletion path; require a fresh proof of identity; revoke sessions; and define what happens to Productivity Up's own todos and related data as well as the auth-provider identity. The identity-provider delete call alone is not the product's deletion semantics. | Clerk classifies account deletion as a sensitive action requiring reverification and exposes user deletion; WorkOS documents step-up reauthentication for irreversible deletes and a permanent delete-user API ([Clerk reverification](https://clerk.com/docs/guides/secure/reverification), [Clerk user management](https://clerk.com/docs/guides/users/managing), [WorkOS reauthentication](https://workos.com/docs/authkit/reauthentication), [WorkOS delete user](https://workos.com/docs/reference/authkit/user/update#delete-a-user)). |

### Important follow-up

| Capability | Product expectation | Why it can follow launch |
| --- | --- | --- |
| Signed-in credential management | Let users change password and verified email, connect/disconnect Google, and prevent removing the last usable sign-in/recovery method. Require recent reauthentication for security-setting changes. | Clerk's account portal treats profile and security management as a normal user surface and requires reverification for password and email changes; WorkOS supports email updates for users not managed by an enterprise identity source ([Clerk Account Portal](https://clerk.com/docs/guides/account-portal/overview), [Clerk reverification](https://clerk.com/docs/guides/secure/reverification), [WorkOS email changes](https://workos.com/docs/authkit/email-changes)). A reset path can preserve access at first launch, but lack of self-service changes creates support debt. |
| Active-session/device management | Show active sessions and allow revoking one or all other devices; pair it with a clear “sign out everywhere” recovery action. | Both providers expose session listing/revocation primitives; Clerk can also notify on unfamiliar-device sign-ins ([Clerk revoke session](https://clerk.com/docs/reference/backend/sessions/revoke-session), [Clerk unauthorized sign-in](https://clerk.com/docs/guides/secure/best-practices/unauthorized-sign-in), [WorkOS session API](https://workos.com/docs/reference/authkit/session)). Current-session logout is launch-critical; a polished device dashboard can follow. |
| Security-event notifications | Notify users after recovery and material authenticator changes, with actionable instructions if the action was not theirs. | NIST requires notifications for account-recovery events and recommends notifications when authenticators are invalidated; Clerk offers unfamiliar-device sign-in notification and one-click session revocation on supported plans ([NIST SP 800-63B account recovery and notifications](https://pages.nist.gov/800-63-4/sp800-63b.html), [Clerk unauthorized sign-in](https://clerk.com/docs/guides/secure/best-practices/unauthorized-sign-in)). This is valuable defense-in-depth but does not replace secure reset and revocation. |
| MFA with a recovery design | Offer MFA after the basic lifecycle is stable, especially if product data or threat level grows. If MFA is enabled, recovery codes/fallback and lost-factor handling are part of the feature, not a later add-on. | Clerk supports required MFA setup as a session task; WorkOS can require TOTP for new and existing non-SSO users ([Clerk session tasks](https://clerk.com/docs/guides/configure/session-tasks), [WorkOS MFA](https://workos.com/docs/authkit/mfa)). NIST treats account recovery as a distinct, risk-assessed process and specifies recovery-code properties and notifications ([NIST SP 800-63B account recovery](https://pages.nist.gov/800-63-4/sp800-63b.html)). |
| Documented support recovery | Decide what support can and cannot do when the user loses inbox/provider access, and how ownership is proven without unsafe security questions or ad hoc database edits. | NIST explicitly rejects knowledge-based security questions for password selection and defines recovery around verified recovery codes/contacts or repeated proofing rather than improvised knowledge checks ([NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)). A low-risk launch can initially state that loss of the only verified inbox/provider is unrecoverable, but that limitation must be deliberate. |

### Optional for the initial B2C release

| Capability | Assessment | Provider evidence |
| --- | --- | --- |
| Passkeys | A strong future replacement/addition, not required to make the already-selected password + Google lifecycle coherent. Domain choice must be stable before production enrollment because passkeys are bound to the registration domain. | WorkOS offers passkeys and progressive enrollment but leaves both disabled by default; it warns to configure the custom production domain first ([WorkOS passkeys](https://workos.com/docs/authkit/passkeys)). |
| Passwordless email codes | An alternate primary method, not an extra recovery requirement. Consider only if it replaces or intentionally complements passwords; do not add it merely to match a provider checklist. | WorkOS describes Magic Auth as a one-time email code and has deprecated magic links because automated email scanners may consume links ([WorkOS modeling](https://workos.com/docs/authkit/modeling-your-app)). Clerk likewise documents passwordless email-code/link strategies separately from passwords ([Clerk sign-up/sign-in options](https://clerk.com/docs/guides/configure/auth-strategies/sign-up-sign-in-options)). |
| More social providers and Google One Tap | Convenience and conversion experiments after standard Google OAuth works reliably. Every added provider expands callback, linking, support, and test permutations. | Clerk offers Google One Tap after Google is configured and supports many social connections; WorkOS supports configurable social login providers ([Clerk Google connection](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/google), [WorkOS AuthKit overview](https://workos.com/docs/authkit/overview)). |
| Hosted account/auth UI | A provider implementation choice, not a user-facing capability requirement. Productivity Up may retain custom UI if it fully owns every state and security edge case. | Clerk offers Account Portal, prebuilt components, or custom API flows; WorkOS offers Hosted UI or public APIs for custom UI ([Clerk Account Portal](https://clerk.com/docs/guides/account-portal/overview), [WorkOS Hosted UI](https://workos.com/docs/authkit/hosted-ui)). |
| Enterprise identity/admin features | SAML/OIDC enterprise SSO, organizations, SCIM/directory provisioning, domain capture, admin impersonation, and organization policy are outside this B2C baseline. | WorkOS explicitly distinguishes consumer email/password, OAuth, and Magic Auth from enterprise SSO, while Clerk separates social connections for all users from enterprise connections for domains/organizations ([WorkOS modeling](https://workos.com/docs/authkit/modeling-your-app), [Clerk authentication strategies](https://clerk.com/docs/guides/configure/auth-strategies/sign-up-sign-in-options)). |

## General expectations versus provider-specific conveniences

The general product contract is that every advertised method reaches one verified app user, yields one bounded and revocable session, supports its realistic recovery cases, and has a safe path through credential changes and deletion. Automatic linking, hosted pages, session-task components, new-device emails, and built-in bot challenges are ways a provider can satisfy parts of that contract; they are not substitutes for deciding the product behavior around them ([Clerk Account Portal](https://clerk.com/docs/guides/account-portal/overview), [Clerk session tasks](https://clerk.com/docs/guides/configure/session-tasks), [WorkOS Hosted UI](https://workos.com/docs/authkit/hosted-ui), [WorkOS AuthKit overview](https://workos.com/docs/authkit/overview)).

Examples of provider-specific conveniences that should not become accidental product requirements:

- Clerk supplies shared OAuth credentials for most providers in development, but production needs the app's own credentials; this is deployment convenience, not evidence that a public domain is required for all local OAuth development ([Clerk social connections](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/overview), [Clerk production deployment](https://clerk.com/docs/guides/development/deployment/production)).
- WorkOS separates staging and production, permits `http://` and `localhost` redirect URIs in staging, requires HTTPS web redirects in production, and does not copy configuration between environments; these are WorkOS environment rules rather than universal B2C capabilities ([WorkOS environments](https://workos.com/docs/authkit/environments), [WorkOS authorization URL](https://workos.com/docs/reference/authkit/authentication/get-authorization-url)).
- Clerk can implement pending post-authentication work as “session tasks,” while WorkOS Hosted UI handles verification, reset, and MFA states outside application code; a custom Better Auth UI will need an equivalent explicit state model even though it will not use those provider primitives ([Clerk session tasks](https://clerk.com/docs/guides/configure/session-tasks), [WorkOS Hosted UI](https://workos.com/docs/authkit/hosted-ui)).

## Decisions Productivity Up must make explicitly

These are the unresolved policy decisions exposed by the baseline; they should become implementation requirements rather than be left to incidental library defaults.

1. **Verification policy:** whether every password registration is blocked until email verification; code versus link; expiry, resend throttling, restart, and mistyped-email behavior. Both comparison providers default toward verified users before normal authentication completes ([Clerk email/password flow](https://clerk.com/docs/guides/development/custom-flows/authentication/email-password), [WorkOS authentication API](https://workos.com/docs/reference/authkit/authentication)).
2. **Google linking policy:** verified-email matching rules; behavior for a pre-existing unverified password user; provider cancellation/denial; mismatched emails; and whether sign-in implicitly creates an account. Clerk treats social sign-in and sign-up as equivalent and both providers gate linking on verified ownership ([Clerk social connections](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/overview), [Clerk OAuth account linking](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/account-linking), [WorkOS identity linking](https://workos.com/docs/authkit/identity-linking)).
3. **Password policy:** minimum/maximum length, compromised-password rejection, password-manager support, rate limits, and enumeration behavior. NIST's current benchmark is at least 15 characters for a password used as a single factor, acceptance of at least 64 characters, no arbitrary composition or periodic-rotation rules, compromised/common-password blocking, and failed-attempt rate limiting ([NIST SP 800-63B password requirements](https://pages.nist.gov/800-63-4/sp800-63b.html)).
4. **Reset aftermath:** whether a successful reset signs the user in, revokes all other sessions, and sends a security notification; plus invalid/expired/already-used token behavior. Clerk exposes revocation of other sessions directly in the reset operation, while NIST requires recovery-event notification in its assurance framework ([Clerk forgot password](https://clerk.com/docs/guides/development/custom-flows/authentication/forgot-password), [NIST SP 800-63B account recovery](https://pages.nist.gov/800-63-4/sp800-63b.html)).
5. **Session policy:** maximum and inactivity lifetime, refresh behavior, current-device versus all-device logout, cache invalidation after auth transitions, and how protected server operations reject stale client state. Clerk frames lifetime as a security/UX tradeoff; WorkOS requires backend token validation on every request ([Clerk session options](https://clerk.com/docs/guides/secure/session-options), [WorkOS sessions](https://workos.com/docs/authkit/sessions)).
6. **Sensitive-action freshness:** how recently the user must have authenticated before password/email changes, linking changes, data export if added, and deletion; and how Google-only users reauthenticate. Both Clerk and WorkOS provide recent-authentication mechanisms for sensitive operations ([Clerk reverification](https://clerk.com/docs/guides/secure/reverification), [WorkOS reauthentication](https://workos.com/docs/authkit/reauthentication)).
7. **Deletion semantics:** hard delete versus any grace period; required confirmation; session revocation; order/atomicity between auth identity and Productivity Up data; retry behavior after partial failure; and what audit information, if any, is retained. Provider deletion primitives only delete the provider user and do not define application-data handling ([Clerk user management](https://clerk.com/docs/guides/users/managing), [WorkOS delete user](https://workos.com/docs/reference/authkit/user/update#delete-a-user)).
8. **Email ownership and operations:** provider-delivered versus application-delivered auth mail, sender/domain branding, per-environment URLs, templates, resend limits, and monitoring/support when mail does not arrive. Both providers support managed or custom delivery, so this remains a product operations choice ([Clerk email templates](https://clerk.com/docs/guides/customizing-clerk/email-sms-templates), [WorkOS custom emails](https://workos.com/docs/authkit/custom-emails)).
9. **MFA and unrecoverable access:** whether MFA is post-launch, which factors/recovery codes it would use, and the support promise when the user loses their only verified inbox, Google identity, or MFA factor. Provider MFA toggles do not remove the need for a recovery policy ([Clerk session tasks](https://clerk.com/docs/guides/configure/session-tasks), [WorkOS MFA](https://workos.com/docs/authkit/mfa), [NIST SP 800-63B account recovery](https://pages.nist.gov/800-63-4/sp800-63b.html)).

## Recommended boundary for the later implementation specification

Treat the nine launch-critical rows above as acceptance-level flows, each with success, cancellation, invalid/expired input, retry/resend, interruption/reload, and cross-device/session consequences specified. Track credential management, device/session management, security notifications, MFA, and support recovery as prioritized follow-ups. Keep passkeys, passwordless codes, extra social providers, provider-hosted UI, and all enterprise identity features outside the first-launch definition unless a separate product decision promotes them.
