# Reactive backend options for near-real-time User state

**Research date:** 2026-08-13  
**Repository baseline:** `main` at `9a8cb435`  
**Scope:** synchronize one User's durable board state across that User's tabs and devices in approximately one second. Lifecycle Reconciliation remains request-triggered. Collaborative editing and proactive per-User jobs are out of scope.

## Answer

Use a **per-User invalidation stream backed by an inexpensive WebSocket service, with PostgreSQL remaining the source of truth and TanStack Query refetching canonical data**. The first implementation should send only coarse invalidation hints, not row data, and should treat delivery as a performance feature rather than a correctness boundary.

This is the smallest architecture that meets the stated bar while preserving Neon PostgreSQL, Drizzle, Better Auth, TanStack Start server functions, and the existing TanStack Query read model. A Cloudflare Worker plus one hibernating Durable Object namespace is a credible concrete host: Durable Objects are available on the Workers Free plan, the Hibernation API keeps client WebSockets connected without idle duration charges, and the current free allowance includes 100,000 Durable Object requests per day and 13,000 GB-s per day. Outgoing WebSocket messages are not charged as requests; incoming messages receive a 20:1 billing ratio. [Cloudflare WebSocket Hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) and [Workers/Durable Objects pricing](https://developers.cloudflare.com/workers/platform/pricing/).

The recommended progression is:

1. **Implement app-published invalidation over an authenticated per-User WebSocket channel.** On each successful state-changing server operation, publish a small scope such as `board`, `taxonomy`, or `session`. Each connected client calls `queryClient.invalidateQueries` for the corresponding keys. TanStack Query marks matching queries stale and background-refetches active queries, which is exactly the desired cache behavior. [TanStack Query invalidation](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation).
2. **Make reconnect, network-resume, and window-focus refetches the recovery path.** Events may be duplicated or missed; neither case can corrupt durable state because event payloads never become authoritative data. TanStack Query already refetches stale queries on focus and reconnect by default. [TanStack Query important defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults).
3. **Add a durable User revision/outbox only if measurements demonstrate an unacceptable missed-event window.** That stronger variant requires the state change and revision/outbox record to commit atomically, so it should be decided together with the database-transaction work rather than introduced speculatively.
4. **Prototype Electric Postgres Sync only if the product later needs live subsets/local querying or broad write sources.** It is the best PostgreSQL-preserving sync engine reviewed, but it is more machinery than invalidation-only synchronization needs.
5. **Do not replace PostgreSQL with Convex solely to obtain this level of reactivity.** Convex is the strongest integrated reactive system reviewed, but its value does not currently outweigh rewriting the database, Drizzle queries, server functions, and authorization paths.

The approximately-one-second target is a healthy-connection service objective, not a consistency guarantee. Before adoption, measure mutation commit to refetched UI at p50/p95 across two browsers and two devices, plus forced disconnect/reconnect behavior. Do not promise a numerical percentile until that deployment-specific test exists.

## Minimum sufficient protocol and security boundary

The recommended stream deliberately does less than a synchronization database:

- The app server authenticates the Better Auth session once and issues a short-lived realtime ticket bound to the canonical User ID. The gateway derives the Durable Object/channel key from that verified identity; the browser cannot select another User's channel.
- Only trusted server-side callers can publish. Client connections are receive-only for invalidation events.
- Events contain an invalidation scope and optionally a monotonic revision, never Bucket, Todo, Tag, Category, session, or profile data.
- All data reads still pass through authenticated TanStack Start server functions whose database predicates enforce per-User isolation. A leaked or forged invalidation hint therefore reveals no record and grants no data access.
- A client invalidates a bounded TanStack Query key set and refetches. It never patches canonical cache data from the event.
- Reconnect, focus, and network-resume refetch the active User state. Duplicate invalidations are harmless.
- Lifecycle Reconciliation still runs when a board request invokes it. If reconciliation changes durable state, the successful request publishes the same board invalidation; no timer or background per-User job is introduced.

This keeps checks on real trust boundaries: one authentication at connection/ticket issuance, one server-derived User channel, one publish credential, and the existing authorization on canonical reads. It avoids repeating row-level authorization inside every event because events carry no rows.

Better Auth uses a traditional cookie session that the server verifies; its cookies are `httpOnly` and production cookies are secure by default. A separate realtime origin should therefore use a short-lived token or same-site proxy rather than attempting to read the cookie in browser JavaScript. Better Auth also documents Safari cross-domain cookie restrictions. [Better Auth session management](https://better-auth.com/docs/concepts/session-management) and [cookie behavior](https://better-auth.com/docs/concepts/cookies).

## Why polling and same-tab cache broadcasting are not enough

Polling every second would meet the latency target only by generating continuous requests and database reads, including while nothing changes. Longer polling stops meeting the target. Focus/reconnect refetching is a necessary repair mechanism, not cross-device reactivity.

TanStack Query's `broadcastQueryClient` synchronizes QueryClient state between same-origin tabs, but it is still explicitly experimental and it cannot synchronize another device. [TanStack Query `broadcastQueryClient`](https://tanstack.com/query/latest/docs/framework/react/plugins/broadcastQueryClient). It can be evaluated later as a connection-count optimization, but it should not be the architecture's foundation.

## Correctness details that apply to every option

1. **Stream after durable success.** Publish only after the state-changing server operation reports success. If a future workflow needs atomic multi-write behavior, the transaction decision is upstream of realtime delivery.
2. **Refetch, do not trust event data.** The event is a cache-invalidating hint. The authenticated server query remains the only source of User-visible durable state.
3. **Bound the channel by User on the server.** Never accept a browser-provided User ID as an authorization decision, even if the event has no rows.
4. **Recover from gaps.** Always refetch on initial subscription, reconnection, network resume, and focus. Add a transactional revision/outbox only if gap duration is observed to violate the UX bar.
5. **Keep Lifecycle Reconciliation explicit.** A reactive subscription observes database changes; it does not create them when time passes. The initial/resumed board request must still invoke reconciliation before returning canonical board state. Convex specifically warns that a subscribed query does not rerun merely because `Date.now()` changes. [Convex best practices](https://docs.convex.dev/understanding/best-practices).
6. **Measure end to end.** Record server commit time, event receipt, refetch completion, and render completion. Test two tabs, two devices, sleep/wake, offline/reconnect, token expiry, and a revoked session.

## Decision gates for the architecture ticket

Choose the recommended app-managed invalidation gateway if all durable writes remain behind Productivity Up server functions and temporary staleness after the rare failed publish is acceptable until reconnect/focus.

Escalate to a transactional revision/outbox if event gaps are frequent or the product later promises a bounded recovery time even without reconnect. Escalate to Electric when multiple write sources, large live subsets, local querying, or offline-oriented reads make invalidation/refetch wasteful. Prefer Supabase when a managed PostgreSQL move is acceptable and its bundled Realtime/free tier is worth the migration. Reconsider Convex only as a whole-backend decision, not as a realtime add-on.

No option should make Lifecycle Reconciliation proactive, and none should weaken per-User database authorization merely because the UI is receiving faster updates.
